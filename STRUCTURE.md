# CodeCeremony — Project Structure

<div align="center">
  <img src="docs/assets/codeceremony-logo.svg" alt="CodeCeremony" width="420">
</div>

This document describes the repository **as it is**. It replaces an earlier
version that described a plan: a Next.js frontend in `apps/web`, PostgreSQL under
`infra/`, and a shared contracts package. None of that shipped, and the reasons
are worth keeping in one place rather than scattered:

- **No PostgreSQL.** The one-command offline rule ruled out a second service. The
  storage is one versioned snapshot file written through an append-only journal.
  About a thousand lines of DDL were written early, never executed by anything,
  and deleted once it was clear they had drifted from the code.
  `backend/migrations/README.md` records that.
- **No Next.js.** A Next *server* would have meant a second runtime in the
  container. A Node *build* is affordable as long as it happens in a stage that
  never reaches the image, so the frontend exists: Vite, React and TypeScript at
  `web/`, built into static files and embedded in the Go binary.
- **No shared contracts package.** There is no codegen step. The contract is
  asserted instead: a test reads the Go router and the TypeScript client and fails
  if they disagree. It exists because the frontend was first written against the
  documented routes and six of the paths it used did not exist.

For why the pieces are arranged this way, read
[`ARCHITECTURE.md`](ARCHITECTURE.md). For the schema, read
[`DATA-MODEL.md`](DATA-MODEL.md).

## 1. Top level

```text
codeceremony/
├── backend/          the Go service: API, embedded frontend, state
├── web/              the Vite/React/TypeScript frontend, built and embedded
├── tests/            cross-process e2e against a real binary
├── scripts/          build, acceptance and asset-generation scripts
├── docs/assets/      brand assets referenced by the documentation
├── src/README.md     where the code went, and why it is not here
├── docker-compose.yml
├── run.py            the acceptance checker
├── .dogfood.toml     claimed tiers and rule requirements
├── design.md         the visual contract the frontend implements
├── rules.md          the event constraints this build answers to
└── *.md              README, ARCHITECTURE, DATA-MODEL, JUDGING, THREAT-MODEL,
                      ACCOUNT-MANAGEMENT, FEATURES, EXPANSION, STRUCTURE
```

`Makefile` was in the plan and never arrived; `ARCHITECTURE.md` section 12 has the
commands that replaced it. `src/README.md` is the one surprise in the root
listing and it explains itself.

## 2. `backend/`

The Go service is the whole backend. Standard library plus one dependency
(`golang.org/x/crypto`, for bcrypt).

| Path | What lives there |
|---|---|
| `cmd/codeceremony/` | entry point, boot order, composition root |
| `internal/domain/` | types and their invariants; imports nothing internal |
| `internal/config/` | environment parsing, defaults, production guard rails |
| `internal/auth/` | password hashing, session cookies, request principals |
| `internal/authz/` | the action vocabulary, the permission resolver, grant checks |
| `internal/store/` | the repository interface, the in-memory implementation, the aggregate |
| `internal/persistence/` | the append-only journal, the snapshot, `Restore` |
| `internal/judging/` | normalization, confidence intervals, Bradley-Terry, fit diagnostics |
| `internal/httpapi/` | routing, middleware, the JSON API, the embedded frontend |
| `internal/httpapi/webassets/` | the `go:embed` tree: SPA build, templates, stylesheet, brand |
| `internal/mailer/` | templates, SMTP and log senders, dispatch with retry, signed webhooks |
| `internal/ratelimit/` | per-account and per-address fixed windows |
| `internal/seed/` | built-in demo data and its fixed credential table |
| `internal/fixtures/` | the shared fixture loader, used by the e2e suite |
| `migrations/` | why there are no migrations; the snapshot format is documented instead |
| `Dockerfile` | three stages: Node build, Go build, distroless runtime |

The dependency direction is one-way and worth stating, because it is the thing
that keeps the domain testable: `domain` imports nothing; `store` and `judging`
import `domain`; `httpapi` imports everything. `httpapi` is the only package
allowed to touch the outside world.

`webassets/spa/` is generated by `scripts/build_frontend.sh` and is **gitignored**,
with only a `.gitkeep` tracked. A binary built from a fresh clone therefore
serves the JSON API and the nine server-rendered pages, and not the React app,
until the frontend has been built once. That is deliberate: the backend has to be
buildable and testable without a Node toolchain installed. Build the frontend
before shipping a binary.

## 3. `web/`

The frontend. It is built once and embedded; nothing in the runtime is Node.

```text
web/
├── src/
│   ├── main.tsx              entry point
│   ├── App.tsx               client-side router, shell, the seven apps
│   ├── apps/                 auth, dashboard, public, account, judge, organizer, admin
│   ├── components/           the design.md inventory, as React
│   ├── lib/                  API client, session, navigation, generated icon table
│   ├── styles/               tokens, base, components, shell, apps
│   └── test/                 Vitest, the component rules and the API contract test
├── public/                   the brand assets, copied to the server at build
├── index.html
├── package.json
└── vite.config.ts            dev server, `/v1` proxy, build outDir
```

`lib/api.ts` is a hand-written typed client, not a generated one. `lib/icons.tsx`
renders only names present in `lib/icons.generated.ts`, which is generated by
`scripts/gen_icons.py` from a pinned Lucide release; a test asserts every name in
the design document exists and that the table contains geometry only.

## 4. `tests/`, `scripts/`, `docs/`

- `tests/e2e.py` builds the binary, boots it on a scratch port and runs 142
  assertions. It is the only suite that exercises process startup, the embedded
  frontend, real HTTP and real headers.
- `scripts/acceptance.sh` starts a portal, runs the acceptance checker against
  `.dogfood.toml` and stops it, in one foreground command.
- `scripts/build_frontend.sh` installs, typechecks, tests, builds and stages the
  SPA into `webassets/spa/`.
- `scripts/gen_icons.py` regenerates the Lucide inventory.
- `docs/assets/` holds the logo and mark that the Markdown banners reference. They
  are vendored copies of the brand files, with the opaque backdrops and white
  letter counters removed; the originals live in the private brand repository.

## 5. What is deliberately absent

Listing these is part of the structure. Each one was considered, and each is a
decision rather than an omission:

- `apps/web/` — the planned frontend location. `web/` replaced it.
- `packages/contracts/` — replaced by the runtime contract test.
- `infra/postgres/`, `backend/migrations/*.sql` — replaced by the snapshot format.
- `src/` as a code root — kept as a pointer document only; the Go module needs its
  `go.mod`, and the frontend needs its own `package.json`.
- A `Makefile` — the scripts do the work, and they are named for what they do.

## 6. Conventions

- Go packages: short, lowercase, one concern each. Exported names follow Go.
- Tests sit beside the code they cover as `_test.go`; the cross-process suite is
  the exception and lives in `tests/`.
- TypeScript files are kebab-case, React components are PascalCase, icon names
  are the Lucide kebab-case names verbatim.
- Route actions are named from the closed vocabulary in `internal/authz`, and
  `GET /v1/permissions` publishes that vocabulary by reading the same maps the
  resolver reads. A route that is not in the matrix does not exist.
- Persistence is never called from `domain`; the aggregate is the only writer.
